FROM BYTES TO BEHAVIOR / 真实证据链

二进制是怎样一步步变成可读逻辑的？

以“存档末字节损坏”为例。每一步都标出本次 EXE 的实际字节、地址或 Ghidra 输出；下方可切换三份存档查看结果。

查看完整指令与 p-code ↗
  1. 01

    先分清：EXE 是规则，存档是数据

    输入

    Ghidra 导入 game_save.exe，分析程序如何读文件和判断条件；运行客户端时，另把 12 字节 .sav 交给它。损坏案例只把存档最后一字节从 6A 改成 00，EXE 本身没有改变。

    EXE  252,764 字节 → 要分析的程序
SAV  47 53 56 31 01 05 07 10 27 00 00 00 → 程序读取的数据
  2. 02

    读文件头，确认它是 x64 的 PE 程序

    识别与装载

    文件从 4D 5A（MZ）开始；偏移 0x3C 指向 0x80，那里是 PE 00 00 签名和 64 86 机器类型。Ghidra 据此选 PE 加载器与 x86-64 语言。镜像基址为 0x140000000，.text 代码节从 0x140001000 开始。

    文件偏移 0x0000: 4D 5A                 → MZ
文件偏移 0x0080: 50 45 00 00 64 86  → PE / 0x8664 (x64)
Ghidra: Portable Executable (PE) / x86:LE:64:default
  3. 03

    沿着调用，找到负责校验的函数

    函数定位

    分析结果中，main 调用读文件函数后，在 0x1400016a0 执行一条 CALL，目标是 0x1400014a4。教学 EXE 保留符号，所以目标直接显示为 inspect_save；真实无符号程序要继续沿调用和字符串查找。

    0x140001679  E8 FA 66 00 00  CALL 0x140007d78  (读文件)
0x1400016a0  E8 FF FD FF FF  CALL 0x1400014a4  (inspect_save)

    这里的地址来自 Ghidra；对应 EXE 文件偏移 0xCA0，可在原始文件中找到同一组 E8 FF FD FF FF。

  4. 04

    把函数里的机器字节解读为指令

    反汇编

    从地址 0x140001534 减去镜像基址，得到 RVA 0x1534；再按节区表换算文件位置：0x1534 − 0x1000 + 0x600 = 0xB34。那里的 30 45 FF 被解码为异或指令；后面是比较、条件跳转和装入错误码 6。

    0x140001534  30 45 FF        XOR byte ptr [RBP + -0x1],AL
0x14000154e  38 45 FF        CMP byte ptr [RBP + -0x1],AL
0x140001551  74 0A           JZ  0x14000155d
0x140001553  B8 06 00 00 00  MOV EAX,0x6
  5. 05

    将指令转成 p-code，再恢复条件

    中间表示

    Ghidra 的 x86 语言描述把指令提升为更统一的操作。下面是本次实际 p-code 的三项关键操作摘要：异或、按比较结果跳转、把常数 6 写入返回寄存器。分析器据此连接数据流和控制流。

    0x140001534  INT_XOR  (累积校验值, 当前字节)
0x140001551  CBRANCH 0x14000155d, 条件位
0x140001553  COPY    0x6 → 返回寄存器

    上面为便于阅读的操作摘要；完整原始 p-code 保留寄存器、临时变量和参数。

  6. 06

    反编译出判断，再用真实运行交叉核对

    结论

    反编译器把上面的分支组织成类 C 表达：计算值与存档第 12 字节不相等时返回 6。把末字节为 00 的存档交给实际 EXE，程序输出校验失败、退出码也是 6。

    Ghidra 原文: else {
               uVar2 = 6;
             }
EXE 实际输出: SAVE REJECTED: checksum mismatch  /  exit code 6
你真正看到的过程：文件头识别 → 地址映射 → 调用定位 → 字节解码 → p-code → 伪代码 → 运行验证核对 PE 字节与偏移 ↗

Ghidra 导入的是编译后的 game_save.exe。下面摘录它实际生成的 inspect_save 伪代码；可与原始报告逐行对照。

01 / WHAT GHIDRA DOES

从“这是什么文件”
到“它为何这样执行”

Ghidra 把不同层次的线索放进同一工作区。下面四项是官方仓库和文档明确支持的核心能力。

01 / PE·ELF·COFF

导入与识别

加载二进制，识别处理器、段、符号与可解析的数据结构，为后续分析建立地址空间。

反汇编

Disassembler
03 / C-LIKE

反编译

Decompiler
04 / API

自动化与扩展

用脚本、无界面分析器和扩展组件处理重复工作，或支持新文件格式与处理器。

02 / WHAT YOU CAN INPUT

把什么交给 Ghidra？
从哪里开始？

先区分“分析对象”和“操作入口”：目标通常是编译产物或运行中的程序；你可以在图形界面、批量命令或调试器中开始分析。

A / SINGLE FILE

单个程序或容器

EXE、DLL、ELF、Mach-O、COFF、APK、DEX 等。使用 File → Import File，确认格式和处理器，再看函数、字符串与引用。

例：收到一个无源码的 Windows 插件。
B / RAW BYTES

原始固件或片段

没有标准文件头的 .bin 也可按 Raw Binary 导入；需要结合设备资料选择处理器、字节序和基址。

例：分析设备升级包中的代码段。
C / COLLECTION

目录与多份样本

用批量导入或 analyzeHeadless 处理目录、多个文件和支持的容器，并运行脚本提取可重复的报告。

例：比较一批软件版本或固件镜像。
D / RUNTIME & PROJECT

运行目标与已有工程

调试器可连接受支持的本机调试后端观察运行状态；已有 Ghidra 项目可继续分析，也可用 Ghidra Server 协作。

例：静态分析后验证某条分支是否执行。
文字问题与网页链接属于研究线索。Ghidra 的主要输入是文件、工程或调试目标。若只有下载地址，先取得有权分析的文件；若只有“它会不会联网？”这样的问题，就把它当作待验证的分析目标。依据：官方导入器、批量模式和调试与协作文档。
