## 01 · 能力与意义

原库提供一个可以真正执行的小语言模型训练实验。它把数据和评测、可改动的训练代码、代理实验规程组织在一起。直接用途是在同一设备与短时间训练预算下，比较模型结构、优化器、批次与训练实现。循环执行依赖外部编程代理。[来源 1](https://github.com/karpathy/autoresearch)

我们的概括是：**由实验反馈驱动的迭代循环，让改动能够运行、比较和追溯。**其价值取决于任务与评测的质量，以及找到的改进能否超过实验和分析成本。训练短期指标改善不自动证明长期训练、其他任务或实际产品也改善。

## 02 · 运行原理

1. 人定义目标、数据、预算、约束与可改范围，先建立基线。
2. 外部编程代理读取代码、日志和失败案例，提出假设并修改代码。
3. 内层程序实际运行。原库训练小语言模型，扩展任务也可以执行普通算法。
4. 按固定评测规则检查结果与资源消耗。
5. 代理按规程记录实验、保留或回退，再利用反馈提出下一次改动。[来源 2](https://github.com/karpathy/autoresearch/blob/master/program.md)

外层大模型主要负责分析和编辑，通常不在每轮重新训练自身。内层是否更新模型权重由研究任务决定。“小模型”描述规模，“专用模型”描述用途，两者不能等同。AI 对原因的解释仍是待验证假设。

## 03 · 内部模块与外部依赖

| 模块 | 职责 | 位置与约束 |
| --- | --- | --- |
| `program.md` | 定义基线、执行、记录、保留和回退的步骤 | 仓库内的规程，由人定义、外部代理读取 |
| `prepare.py` | 数据准备、分词器、数据加载、预算常量与 `evaluate_bpb` | 仓库内；规程要求不改评测 |
| `train.py` | GPT、优化器与训练循环，调用评测并打印指标 | 仓库内；代理主要修改对象 |
| 外部编程代理 | 分析、编辑、工具调用与持续执行 | 需另行启动，仓库不自带通用模型 API 调度服务 |
| 运行环境 | Python / PyTorch、单块 NVIDIA GPU、uv | 上游在 H100 测试；本机兼容性仍需跑通验证 |
| Git / 日志 / `results.tsv` | 关联代码版本、记录分数、资源和状态 | 由代理按规程操作 |

原库训练计时约 300 秒，启动、编译与最终验证另计；`val_bpb` 衡量验证文本每字节的预测代价，越低越好。不同设备的短时间结果不宜直接排名。[来源 1](https://github.com/karpathy/autoresearch)、[来源 3](https://github.com/karpathy/autoresearch/blob/master/prepare.py)

评测函数在训练进程内调用，“不可修改评测”是规程约定，没有独立权限隔离保证。本次核对的默认 `train.py` 输出指标，没有自动保存模型权重的步骤；若需要交付权重，应补充保存、加载与复验流程。[来源 2](https://github.com/karpathy/autoresearch/blob/master/program.md)、[来源 4](https://github.com/karpathy/autoresearch/blob/master/train.py)

## 04 · 软件、仿真、硬件方向

**下列均是本项目提出的迁移构想。**上游不提供这些领域的现成适配器，当前项目也没有证明它们普遍有效。表中是候选改动与验收思路，不是已取得的改进。

### 软件方向

| 任务 | 可以尝试的改动 | 怎样判断有效 |
| --- | --- | --- |
| 网页性能 | 组件、资源加载、缓存 | 功能和画面完整，加载、交互与资源开销改善 |
| 数据库查询 | 查询结构、索引方案 | 查询结果一致，代表性工作负载下延迟与资源改善 |
| 程序加速 | 算法、数据结构、执行实现 | 正确性通过，耗时或内存改善 |
| 图片与音频压缩 | 编码方法、配置 | 约定保真度下比较体积、耗时和成本 |
| 文档信息提取 | 解析、识别、校验与处理流程 | 用独立标注检查逐字段正确性和成本 |
| 知识库问答 | 检索、提示与验证流程 | 答案质量、引用依据、延迟和成本 |
| 搜索与推荐 | 召回与排序流程 | 独立离线评测；真实收益另需线上验证 |
| 排班与资源调度 | 求解方法、启发式与约束表达 | 约束满足、完成效率与总成本 |

这些任务多数可以优化代码或处理流程，不必训练新的模型。是否需要大模型参与，要与已有工具和普通搜索做同预算比较。[网页的 12 种场景详解](../../sites/005-autoresearch/understanding.html#use-cases)包含每类的分析材料、改动范围与适用判断。

### 仿真与 3D 方向

| 候选任务 | 内层执行什么 | 需要的评估 |
| --- | --- | --- |
| 游戏角色行为 | 策略执行或学习，可包含强化学习 | 新关卡、不同种子下的完成率与违规情况 |
| 3D 渲染与画面性能 | 渲染代码、资源与配置 | 同设备、同视角下的帧时间、画质与内存 |
| 导航、自动驾驶与多机避碰 | 规划、避障与协作策略 | 未见场景中的碰撞、任务完成、耗时与资源 |
| 仓储、产线与工程设计 | 调度、离散事件或工程求解 | 满足真实约束，比较吞吐、成本或设计指标 |

画面展示、物理模拟、感知和策略学习是不同部分。选择模拟器取决于任务：物理与传感器、驾驶、离散事件或工程求解的需求不同。

候选基础工具各有官方说明：[Gazebo](https://gazebosim.org/libs/sim/)、[Isaac Lab](https://isaac-sim.github.io/IsaacLab/main/index.html)、[CARLA](https://carla.org/)、[SimPy](https://simpy.readthedocs.io/en/latest/)、[OpenMDAO](https://openmdao.org/)。这是按职责建立的接入方向，未在本机安装或完成与本项目的集成验证。

### 硬件协同方向

| 候选任务 | 研究对象 | 现实验证条件 |
| --- | --- | --- |
| 相机与视觉检测 | 识别流程、光照适应、误漏检 | 代表性录像、标注与独立实景测试 |
| 多传感器融合与校准 | 相机、测距、IMU 等输入的一致性 | 标定与时序基准、噪声、遮挡、数据丢失 |
| 移动机器人与协作 | 导航、避障、任务协调 | 设备约束、回放与仿真、受控场地验证 |
| 边缘端模型部署 | 模型压缩、推理配置与执行效率 | 任务质量、延迟、功耗和内存共同测量 |
| 设备测试与环境控制 | 测试配置、诊断或控制方法 | 设备接口、校准数据和明确运行边界 |

产品价值需要来自特定条件下可复验的改善。已有智能摄像头或控制器仍可以作为成熟基线；单纯重复已有功能，不能说明引入 AI 研究循环值得投入。硬件可以提供真实数据和验证环境，开始研究不要求先购买设备。

## 05 · 仿真接入的数据流

内层环境按时间推进：**物理环境 → 传感器模型 → 感知 → 决策策略 → 动作执行 → 新状态**，新状态继续产生下一时刻的观测；每轮结束产生评测和失败记录。外层代理据此选择方法改动，再运行下一轮。

- 仿真真值用于物理、渲染与评估。
- 感知和策略只能读取任务接口允许的观测，例如相机图像、测距或 IMU 数据。
- 直接使用真实坐标可以构成理想条件基线，但不能证明图像识别或真实感知能力。
- 网页适合承载观察、配置和回放；真实结论还依赖动力学、传感器误差、延迟与校准。
- 迁移可分为软件仿真、硬件在环和受控实测。具体阶段按任务需要选择；仿真通过仍需现实复验。

Gazebo 提供物理、渲染、传感器与噪声模型等基础能力。[来源 5](https://gazebosim.org/libs/sim/) PX4 区分软件在环（控制程序在计算机运行）和硬件在环（真实控制器参与模拟环境）。[来源 6](https://docs.px4.io/main/en/simulation/) 这些机制说明可以建立接入层，不代表 Autoresearch 自带这些组件。

## 06 · 产品化应复用与重建什么

**可复用的流程：** 提出假设、执行实验、采集指标、代码版本、保留或回退。产品化还可建设任务队列、总预算、并行实验、评测隔离、数据版本、回放和审阅。这些是扩展需求，原库没有提供完整实现。

**每个领域需要适配：** 问题与数据、模拟器或设备接口、可改算法与代码、约束和可信评测、最终独立验收场景。应复用成熟模拟器、求解器或实验管理工具，不必全部自行重建。

**候选产品：** 软件性能实验台、AI 流程评测与优化、仿真策略实验室、设备测试优化。交付应包括实际代码或配置、必要时的模型权重、可复查的评测报告与回退版本。用户需求和净收益尚待验证。

## 07 · 适用判断与验证

适合尝试的前提：有足够的分析材料、有多种值得比较的改法、实验可重复、评分可信、运行成本可控。

验证应包含：成熟方案或普通搜索基线、相同总预算、重复实验、未参与选优的独立测试，以及维护和算力成本。原库五分钟训练预算只是一个具体协议；新场景应定义适合自己的公平预算。

只有少量阈值时，先枚举或参数搜索可能更划算。主观目标、失真的环境与评分、只有预设动画而没有实验结果，都不足以证明 AI 带来了改善。即使实验没有改善，也应记录失败和结论。

## 08 · 当前状态与下一步

- **V1 已实现：** 三维运动、直接读取坐标的规则和光学标记教学效果；没有真实感知与物理捕获。
- **V0.5 已实现：** 相机渲染画面的变化检测、规则比较、批量实验、记录与回放；算法由人预设。
- **尚未完成：** 物体识别、定位、真实硬件校准、上游模型训练、AI 自动改进循环与商业收益验证。
- **建议下一步：** 选择一项已有代码或数据的任务，跑出可靠基线，冻结评测并限定改动和预算，让代理尝试，再独立复测。小语言模型训练是与原库最直接对应的可选任务，已有[设计但未运行](TASK-DESIGN.md)。

上述项目状态依据本仓库的[研究记录](README.md)和[V0.5 实测](WORKBENCH.md)，不是上游能力或外部产品实测。
