## 1. 选定的任务

**固定相机观察一个持续运动的三维场景，程序发现持续过暗、细节明显丢失的画面，提示检查，并在画面恢复后结束提示。AI 通过重复实验，寻找漏报更少、误报更少的观察规则。**

这是一项独立的录像质量巡检任务。无人机在这里仅作为正常运动的场景内容；没有物体身份、物体位置、飞行路径估计或设备控制输出。

用户需要回答的是：“这段画面是否满足本实验事先约定的质量标准？哪些片段值得检查？”识别对象是画面的可见症状。单凭过暗或细节不足，不能确定是灯光、镜头、场景本身还是设备故障造成。

第一版只研究两个问题：

- **持续过暗：**出现持续的严重亮度不足，画面可见细节明显减少。
- **细节明显丢失：**相对可确认的清晰参考片段，画面出现持续的明显模糊。

首版不承诺判断镜头遮挡的具体原因，也不根据“连续图像相同”判断摄像头卡死。静止场景同样可以产生相同画面；输入中断将来需要独立的帧到达记录，属于另一项任务。

## 2. 为什么选它

| 判断依据 | 对本项目的意义 |
| --- | --- |
| 能复用现有场景、相机、噪声、时间轴与回放 | 工作集中到任务与自动实验循环 |
| 画面异常可以独立生成、保存和人工复核 | 能给评估器提供独立答案 |
| 运动、正常明暗变化与噪声容易影响简单统计 | 有可以检验的失败情况和改进空间，但不预设一定能改进 |
| 输出是用户能看懂的事件及依据 | 可以查看异常前、异常中、恢复后的画面 |
| 可用简单规则建立合理基线 | 首轮无需训练大模型，实验成本容易控制 |

这是依据当前资产与研究目标作出的任务选择，并非市场上尚无人实现的功能。价值需要由“减少了多少人工调试、在新数据上改善多少”验证。尚未证明它比成熟摄像头的质量诊断更好。

## 3. 用户看到的完整过程

以下是待实现的演示脚本，不是已经运行的结果。

1. **正常运行：**场景中的物体运动，相机画面清楚，状态显示“未发现约定的质量异常”。
2. **施加问题：**对相机画面加入一段持续严重变暗或模糊。全景仍能正常观看，相机画面受到影响。
3. **观察与提示：**算法读取实际受影响的图像，显示“画面过暗”或“细节不足”，同时展示判断所依据的统计和持续时间。
4. **恢复：**撤去影响。算法独立判断恢复，记录异常开始、提示送达与恢复时刻。
5. **自动研究：**AI 阅读开发集的失败样本，修改候选规则；同一批输入同时评价基线与候选，展示保留或撤销的理由。
6. **最终检验：**冻结候选，在从未用于修改或选优的数据上验证。没有改善时如实保留基线，显示“本次未找到有效改进”。

网页拟分为三个主要区域：原始相机画面与回放、观察结果与证据、真实实验日志。日志至少包含候选编号、修改摘要、基线与候选分数、保留/撤销理由、文件摘要和运行状态。没有发生的实验不显示为已完成。

## 4. 输入、输出与答案的边界

| 角色 | 可以获得什么 | 产生什么 |
| --- | --- | --- |
| 场景与扰动生成器 | 场景配置、随机数、扰动安排 | 持久化图像序列；独立答案文件 |
| 观察算法 | 已送达图像、相邻样本间隔、序号；每段重新初始化 | 质量状态、可解释统计、异常与恢复事件 |
| 独立评估器 | 算法输出、答案、送达时间 | 发现、漏报、误报、发现与恢复延迟 |
| 实验代理 | 开发数据和开发评测反馈、允许修改的候选规则 | 下一份候选规则与修改理由 |
| 用户界面 | 图像、算法输出、评估报告 | 同步展示与回放 |

候选算法不接收世界坐标、物体名称、扰动类型、扰动起止时间、场景种子、标签或分组名称。算法只描述送达画面；没有到达的图像不能参与判断。

拟定状态：`normal`（未发现约定异常）、`degraded`（发现质量异常）、`uncertain`（证据不足）。输出的“过暗”“细节不足”是画面症状，不是设备故障诊断；正常状态也不代表所有视觉任务都能可靠完成。首帧及缺少必要参考时允许返回证据不足。

## 5. 算法与 AI 各自负责什么

### 基线与候选算法

首版采用可解释的整幅图像统计：亮度分布、细节变化量及连续帧的稳定性。先实现一个正常调试过的固定基线，避免故意使用明显不合理的基线来制造改善。

基线参数只用开发集确定，随后冻结。候选改动范围为这两个画面症状的统计规则、时间平滑、进入与退出异常的判定。所有输出仍限定为整幅画面质量，不产生物体区域、类别、位置或跟踪结果。

图像的二阶变化可以作为细节线索，OpenCV 的 [Laplacian 文档](https://docs.opencv.org/4.x/d5/db5/tutorial_laplace_operator.html)介绍了该算子。将它用于本任务是待验证的设计选择：噪声会产生高频变化，低纹理场景也可能天然缺少细节，不能把一个数值直接当作“已确诊失焦”。无法区分的片段允许提示证据不足。

### AI 实验代理

AI 在实验外层读取反馈并修改规则；实时画面仍交给被测试的算法处理。首轮不训练大语言模型，也不要求摄像头每一帧都调用大模型。

Autoresearch 的原任务是外部代理改动语言模型训练代码、执行固定预算的训练、根据指标保留或回退。这里借鉴其固定评测与迭代方式；相机任务和运行器需要另行开发，不能称为直接运行了源仓库的训练任务。[上游 README](https://github.com/karpathy/autoresearch#how-it-works)

## 6. 数据与答案设计

第一批拟生成 **72 段、每段 24 秒**的记录，分为开发、选优、最终检验三组，各 24 段。以下数量为设计计划，当前尚无这些样本。

每组包含六类条件，每类四段：

| 条件 | 期望行为 |
| --- | --- |
| 正常画面，场景持续运动 | 不产生质量异常事件 |
| 短时变暗，随后恢复且整体仍满足约定标准 | 不产生持续异常事件 |
| 持续严重过暗 | 发现质量异常，恢复后结束 |
| 持续明显细节丢失 | 发现质量异常，恢复后结束 |
| 加入噪声但仍满足约定标准 | 不把噪声的变化本身当成质量异常 |
| 低纹理或原因无法区分的片段 | 展示证据不足，单独报告不确定情况 |

实施要求：

- 用不同的场景、轨迹与扰动安排分别生成三组；同一段录像及其近似变体不能跨组。
- 异常起止时刻和持续时间变化；不能沿用当前演示所有片段都在第 4 秒、第 8 秒变化的安排。候选不获得绝对场景时间。
- 独立保存最终图像输入、答案、生成配置、版本和文件摘要。同一输入用于全部候选，避免每次重绘差异影响比较。现有 JSON 没有嵌入图像，不能直接承担这一职责。
- 生成器提供扰动安排，人工检查可见效果是否符合预先写明的质量标准。注入了某种扰动，不自动意味着其强度已达到异常程度。
- 使用最短 1 秒的持续异常作为首版事件定义；标注记录可见异常开始 `t0`、满足持续条件的时刻 `t0 + 1s` 与结束时刻。过短扰动不构成正事件。这是实验约定，不是行业标准。
- 歧义片段单列，不强行给出故障原因。确定片段上的 `uncertain` 不能逃避评分：异常未发现仍算漏报，正常片段另报不确定时长。
- 开发集供代理查看并调整；选优集只由固定运行器按预定方式比较，首轮不向代理回传选优反馈；最终集不参与任何候选生成与选择。

72 段仅用于验证流程，不能证明真实部署能力。真实录像阶段需要重新定义答案并独立标注；模拟结果和真实结果分开报告。

## 7. 如何评分与决定保留

以下为拟定首版评测协议，尚未运行。实施前冻结答案、计分规则和容差；之后的协议修改须升版本并重跑所有基线。

### 事件对应

- 以状态从非异常进入异常作为一条事件。算法持续保持异常时不重复增加事件数。
- 报警所用图像的采样时刻位于 `t0` 至 `t0 + 2s`，才可以匹配该异常。允许算法在持续条件成立前提前发现；一次报警只匹配一次异常。
- 正常片段上的报警、异常发生前的报警以及同一异常的额外报警均计入误报。错过匹配窗口的报警也不补记为发现。
- 评估器用固定采样与送达安排判断数据已齐，再确定漏报。异常期间一直报正常或证据不足，都不能获得发现分。
- 发现延迟取 `max(0, 报警送达时刻 - (t0 + 1s))`；另保存相对可见异常开始 `t0` 的原始延迟。报告明确两种起点，避免混用。
- 恢复延迟从答案的异常结束到算法回到正常计算。漏报恢复、正常时长被长期标为异常，也要计入结果；只报一次后永久保持异常不能通过。

### 主指标与约束

- **主指标：**全部确定片段上的事件 F1，`2 × TP / (2 × TP + FP + FN)`，越高越好。数据中必须有正事件；全空输出不能获得高分。
- **同时展示：**两种异常各自的发现率、正常片段每分钟误报、正常时长被标异常的比例、发现与恢复延迟的中位数和 P95、不确定时长比例、处理耗时。
- **初始验收目标：**两种异常各自发现率至少 90%；正常片段每分钟误报不超过 0.2 次；正常时长被标异常不超过 5%；发现与恢复延迟 P95 各不超过 1 秒；确定片段不确定时长不超过 10%。这些是小规模演示的设计目标，未达到或未测量时如实标注。报告须同时列样本数，不能用少量样本宣称生产可靠性。
- **执行有效性：**异常、超时、输出不合规或没有必要的延迟数据，均为无效候选，不能按零延迟获胜。首轮按 5 Hz 输入，在约定测试设备上记录耗时，并以每帧 P95 不超过 100 ms 为初始计算预算；设备、分辨率及测量方法需一并固定。
- **保留规则：**先满足所有验收与执行约束，再与同组冻结基线比较主指标。没有严格改善则保留基线；并列候选按固定的较低 P95 发现延迟、较低 P95 处理耗时、候选编号顺序选定。

## 8. 一次真实的自动研究应留下什么

首轮计划最多尝试十个候选。候选数量与运行预算须在运行前确定，不因最后的分数临时延长；本设计未启动任何模型调用或付费运行。

1. 固定输入、答案、评分器、合理基线和运行环境，记录摘要。
2. 代理根据开发反馈提出一个改动，只修改指定候选规则文件。
3. 在隔离的执行环境中运行；不给候选访问答案、完整项目记录或外部网络的权限。
4. 保存候选内容、原始输出、开发得分、耗时、失败原因和保留/撤销决定。
5. 尝试结束后，固定运行器在选优组中比较有效候选和基线，按既定规则冻结一个版本。
6. 最终组只检验这一个版本与基线。不根据最终组反馈再修改本轮候选；若未改善，报告未通过，而不是继续调到通过。

网页的实验日志应来自真实运行产物。自动枚举参数可以单独作为对照，但不能被标成“AI 提出了新算法”。
